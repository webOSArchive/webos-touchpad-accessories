1.1.9 release notes  (NOT part of the stanza -- for the changelog / feed post)
================================================================================

Fixes a USB drive that mounts fine but shows up EMPTY in Internalz Pro.

The stick used to be mounted at /media/internal/usbdrive. That looked like the
right home -- /media/internal is the writable user partition every file manager
browses -- but it is the one place the drive cannot be seen from.

Internalz Pro's backend, FileMgr-Service, does not use readdir for anything
under /media/internal. It shells out to MTOOLS (`mdir` against
`drive A: file="/dev/mapper/store-media"`) whenever the caller asks to hide
hidden files, which is Internalz's default. mtools parses the internal
partition's FAT directly and is blind to the kernel's mount table, so a drive
mounted at a subdirectory of that volume lists as an empty folder -- while
writes into it land on internal storage underneath the mountpoint. Verified on
device: `mdir -f "A:/usbdrive/"` returns only `.` and `..` for a directory that
demonstrably has files in it.

  * The drive now mounts at /media/usb, outside the media partition, which takes
    FileMgr's ordinary readdir path. Listing, hidden-file filtering, and
    read/write/create/delete through the service all verified on webOS 3.0.5 and
    webOS CE 3.1.0.
  * Creating that mountpoint needs a writable root fs. The installer already
    remounts rw, and the daemon falls back to the old in-partition path if the
    directory cannot be created, so a locked-down device still mounts.

Also raises MaxWebOSVersion to 3.1.9 so the app is offered on webOS CE 3.1.x.
It was capped at 3.0.9, which excluded the CE builds entirely.

Upgrade note: install over the top and reboot as usual. If a drive is mounted
when you upgrade, the old /media/internal/usbdrive mount is cleared by the
post-install reboot. Browse to /media/usb afterwards -- and note webOS's own
media indexer only scans /media/internal, so photos and music on the stick no
longer appear in the stock Photos/Music apps.

If the panel shows no drive at all: that is usually not the mount. The TouchPad's
OTG controller can wedge (dmesg shows "device not accepting address N, error
-110" and the port drops to low power), and only a controller cycle clears it --
switch USB Host off, wait a few seconds, switch it back on.

1.1.8 release notes  (NOT part of the stanza -- for the changelog / feed post)
================================================================================

Fixes a bug that made game controllers appear broken in OTHER apps.

The device monitor behind the "input received" indicator used to open each
controller EXCLUSIVELY (EVIOCGRAB). An exclusive grab starves every other reader
silently -- no error, just no events -- so a controller you had just verified in
this panel was then dead in any game you launched afterwards, while still
enumerating and identifying perfectly. Every visible sign said the hardware was
fine, which is what made it so hard to pin down.

  * The monitor now reads input devices SHARED and never grabs. Nothing this app
    does can take a controller away from a game.
  * The panel releases its monitor as soon as it is no longer in front, rather
    than only when it is closed, so nothing keeps running behind you.
  * A monitor orphaned by an app update is cleaned up on the next daemon start.

Also restores the 1.1.4 daemon performance work, which an earlier build had
inadvertently reverted. The background daemon is builtin-only on its idle path
again instead of forking ~15 processes a second; measured on device at 41 -> 15
jiffies per 10 s. That fork storm is what used to stall games about once a
second, so this matters well beyond tidiness.

Upgrade note: install over the top via Preware / WebOS Quick Install and reboot,
as usual. No settings are lost.

MAINTAINER WARNING -- read before editing this app
--------------------------------------------------------------------------------

PULL BEFORE YOU EDIT usbctl-watchd.sh, and diff against the shipped ipk.

The 1.1.4 fork-storm fix landed in PR #1 (usbctl-watchd-perf). Work done from a
clone that predated that merge started from the pre-1.1.4 file, silently reverted
the fix, and shipped it as 1.1.7 -- the daemon went back to forking ~15 processes
a second on its idle path, which is exactly what stalls games about once a
second. Nothing about the file looks wrong when you do this; it just quietly
performs like the old one.

The idle path of this daemon is load-bearing and easy to regress by accident.
Verify by MEASUREMENT rather than reading: sample /proc/<pid>/stat over 10s and
sum fields 14-17. Fields 16-17 are the point -- a shell script's forks are child
processes, so their CPU lands in cutime/cstime, and summing only utime/stime will
show a fork storm as near-zero.
